# Заявки с сайта → SEVER App: состояние API и контракт интеграции

Проверено по коду 09.10.2026. **Этот документ обязателен к обновлению при каждом изменении описанных здесь маршрутов, DTO, прав, авторизации или логики заказа.** Правило также закреплено в корневом `AGENTS.md`. Примеры ниже относятся к текущему коду, а не к обещанному публичному API.

## Что работает сейчас

### Финансовые правила заказа

`PUT /api/projects/:id/estimate-lines` принимает `{lines, settings?}`, где `settings` содержит `totalDiscountType` и `totalDiscountValue`. Переданные строки и общая скидка сохраняются атомарно; прежнее тело `{lines}` совместимо и не меняет общую скидку. Цена и себестоимость неотрицательны, процент скидки не выше 100, источник строки не дублируется. Для ненулевой скидки `fixed_rsd` нужен настроенный курс. Удаление исходной позиции из клиентской сметы сохраняет скрытую строку, чтобы позиция не появилась снова из резервации. Плановая работа команды входит в первоначальный расчёт счёта, так же как после сохранения сметы.

Финансы, Apex и прежние `GET /api/finance/projects/:id`, `GET /api/finance/debts` используют расчёт billing: цена по смете минус оплаты клиента. В список клиентских долгов попадают финансово учитываемые проекты `awaiting_payment` и `completed`. Долг подрядчику учитывает частичные платежи; расходы, связанные с назначением или подрядчиком, погашают плановое обязательство и не прибавляются к себестоимости второй раз. Прочие расходы увеличивают себестоимость.

`POST /api/finance/transactions` принимает необязательный `requestKey` (UUID). Повтор с тем же ключом и данными возвращает существующую операцию без повторного движения денег; другие данные с тем же ключом дают 409. Валюта должна совпадать со счётом, сумма положительная с точностью до двух знаков. Проект, единица и принадлежность назначения/подрядчика проверяются через публичные сервисы.

`PATCH /api/finance/transactions/:id` теперь создаёт исправление: возвращается **новый ID**, `replacesTransactionId` указывает на оригинал. Оригинал сторнируется, его сумма и снимок FX сохраняются. Новая запись использует исходный курс. `POST /api/finance/transactions/:id/void` идемпотентен. Для повторного изменения/сторно клиент использует ID из ответа PATCH. Список по умолчанию исключает сторнированные записи; `includeVoided=true` показывает историю.

`finance.manage` даёт полный доступ к операциям. Ограниченные Operations-права требуют `projectId`: payroll управляет только связанными выплатами команде, finance — оплатами клиента и подрядчиков. Чтение скрывает категории другого блока, закупки, ремонты и балансы счетов; доступ к чужому проекту запрещён, кроме пользователей с глобальными финансовыми правами, `projects.manage` или разрешением видеть все проекты в Operations. Без этого требуется активное назначение на проект. Прямое изменение `paidEUR` назначения и `PUT /api/contractor-items/paid` отклоняются: новые выплаты проводятся через финансовый журнал, а старые отметки без проводок остаются совместимыми историческими данными.

Новые версии смет сохраняют `rateToEUR` и `company` вместе с содержимым и итогом. Старые версии без снимка курса не позволяют достоверно восстановить сумму в иностранной валюте; их EUR-итог сохраняется, экспорт в иностранной валюте требует нового документа.

SEVER хранит клиента, проект (заказ в операционном процессе), резервации оборудования и строки сметы. Текущие маршруты рассчитаны на авторизованного пользователя приложения. Единого приёмника заявок с сайта **нет**. Обе разновидности сообщения из Telegram не распознаются и автоматически в проект не превращаются. Отдельной сущности «заявка на подбор» тоже нет.

Расчёт доставки берёт действующую максимальную цену EVRO PREMIJUM BMB 95 или EVRO DIZEL из самой свежей публикации Министерства внутренней и внешней торговли Сербии, если цена не передана вручную. Цена из RSD переводится в EUR по текущему курсу RSD, настроенному в SEVER. Итоговая себестоимость — стоимость топлива плюс настроенная для автомобиля амортизация за километр. В экономике проекта каждый добавленный автомобиль сохраняется отдельной ручной строкой `Доставка`; итоговую себестоимость строки можно скорректировать перед добавлением. Это внутренний авторизованный маршрут приложения и не является приёмником заказа с сайта.

`CreateProjectInput`: обязательны `name` и существующий `clientId` (UUID). `name` считается базовым именем: сервис сохраняет его как `ProjectDTO.baseName`, а `ProjectDTO.name` формирует по глобальному шаблону названия проекта. Шаблон поддерживает `[name]`, `[dates]`, `[start.date]`, `[start.time]`, `[end.date]`, `[end.time]`, `[location]` и `[client]`; изменение шаблона пересобирает имена существующих проектов. Необязательны `startsAt`, `endsAt` (ISO 8601 с часовым поясом), `venueId`, `note`, `financeTracked` и поля дресс-кода. Период может отсутствовать для заявки на подбор. `ProjectDTO` возвращает `id`, `status`, `startsAt`, `endsAt` и прочие поля, включая nullable-метаданные серии `seriesId`, `seriesOccurrenceKey`, `seriesTemplateVersion`. `contacts` клиента — одна текстовая строка: отдельных полей телефона, Instagram и предпочтительного канала связи пока нет. У проекта нет полей для адреса доставки, времени выдачи и возврата отдельно от периода, исходного ID заявки или итоговой цены сайта. `note` может временно хранить эти сведения, но это не структурированный контракт.

Регулярная серия является только расписанием и шаблоном: у неё нет общего финансового баланса. Материализованные повторения имеют разные `projectId`, поэтому резервации, сметы, транзакции, платежи и операционные факты ведутся отдельно. Массовое изменение сначала создаёт неизменяемый предпросмотр; нетронутые поля обновляются автоматически, локально изменённые поля требуют решения `keep_local` или `use_series`. Транзакции и фактические операции этим механизмом не переносятся и не объединяются.

У позиции команды (`ProjectRoleDTO`) есть необязательный внутренний `comment` длиной до 2000 символов. Он отображается в карточке проекта и Telegram-приглашении кандидату, переносится при дублировании проекта, но не попадает в строки сметы, версии сметы, PDF и другие клиентские документы. Изменение комментария обновляет ещё не закрытые Telegram-приглашения.

Резервация требует **внутренний `modelId`**, количество `qty` — положительное целое. Если время опущено, сервис берёт даты проекта. Конфликт доступности не блокирует создание: он создаёт проблему для Apex. Название товара в сообщении Telegram не является надёжным идентификатором модели. Смета хранит `qty`, `priceEUR`, скидки и итоговые настройки отдельно от резерваций; замена строк через `PUT` удаляет прежние строки этого проекта. Настройка общей скидки сама по себе не фиксирует присланные сайтом `540 €` как подтверждённую цену.

### Авторизация и ошибки

`Authorization: Bearer <session>` — сессия пользователя после `POST /api/auth/login` (email/пароль) либо проверенные Telegram Mini App `initData`. Доступ определяется правами этого пользователя. `AUTH_DEV_BYPASS` предназначен для локальной разработки и **не является** механизмом интеграции. Отдельного токена/API-ключа с ограниченными правами для сайта сейчас нет. CORS разрешает происхождения браузера, но это не авторизация. Секрет пользователя нельзя помещать в браузерный код сайта.

Права `apex.projectProblems.notify` и `apex.clientFollowups.notify` относятся только к внутренним агрегированным Telegram-сводкам о проблемах приближающихся проектов и работе с клиентами. Они не дают сайту доступа к маршрутам создания или изменения заказов.

Ошибка имеет вид `{ "error": { "code": "validation_error", "message": "…", "details": … } }`; `details` есть не всегда. Возможны `400` (неверные поля), `401` (нет сессии), `403` (нет права), `404`, `409`, `500`, а при обслуживании базы `503`. У нынешних отдельных `POST` нет гарантии идемпотентности: повторная доставка создаст дубликаты.

## Что подготовить на стороне сайта

1. Отправлять **структурированный JSON с сервера сайта**, в момент появления заявки. Текст Telegram оставить лишь уведомлением для человека. Передавать стабильный уникальный `externalOrderId`/`externalLeadId` и тип `rental_order` либо `selection_request`.
2. Передавать исходные поля без потерь: имя, телефон в исходном виде и по возможности нормализованный E.164, предпочтительный способ связи, Instagram, описание события; для аренды — строки `{siteProductId, name, quantity, unitDailyPriceEUR}`, даты аренды, отдельные дату/время выдачи и возврата, адрес и способ доставки, валюту, дневную цену, скидку и объявленный итог. Не выводить количество из текста вроде `2× … × 1`: нужен явный числовой `quantity`.
3. Указывать часовой пояс события/выдачи/возврата (например, `Europe/Belgrade`) и правила расчёта дней. Отправлять ISO 8601 с offset для конкретных моментов. Проверить арифметику цены и скидки: `90 × 7 × 0,86 = 541,80`, тогда как в образце написано `540`; надо передавать применённое правило округления либо считать итог сайта отдельным исходным значением для сверки.
4. Согласовать таблицу соответствия `siteProductId → modelId` SEVER для каждого товара. Для неизвестного или неоднозначного товара сохранять заявку на ручной разбор, не выбирать модель по похожему имени.
5. Хранить секрет только на сервере, отправлять по HTTPS, повторять запрос при временных ошибках с тем же внешним ID и сохранять ответ SEVER. Не повторять создание с новым ID после таймаута.

## Что добавить в SEVER до безопасного автосоздания

Это **планируемый контракт, не существующий маршрут**. Рекомендуемая граница — отдельный серверный `POST /api/integrations/site/requests` с ограниченным секретом интеграции, проверкой и журналом внешних ID. Он должен атомарно либо повторно возвращать один результат для пары `(source, externalId)`, без повторного клиента, проекта или резерваций. При том же ID и другом содержимом — ошибка конфликта. Секрету не нужны общие права `finance.manage` или `projects.manage`.

Предлагаемая форма входа:

```json
{
  "source": "sever-website",
  "externalId": "order-12345",
  "kind": "rental_order",
  "customer": {"name": "Sasha", "phone": "+38190584985034", "preferredContact": "call", "instagram": "@event_out"},
  "rental": {
    "startsAt": "2026-08-16T00:00:00+02:00",
    "endsAt": "2026-08-23T00:00:00+02:00",
    "pickupAt": "2026-08-16T14:10:00+02:00",
    "returnAt": "2026-08-23T05:10:00+02:00",
    "billingDays": 7,
    "items": [{"siteProductId": "nec-m403h", "name": "NEC M403H", "quantity": 1, "unitDailyPriceEUR": 30}],
    "dailyPriceEUR": 90, "discountPercent": 14, "quotedTotalEUR": 540,
    "delivery": {"mode": "address", "address": "Moscow - Ulitsa Mira"}
  }
}
```

Для `selection_request` вместо `rental` передавать `eventDescription` (например, «Svadba»); даты и оборудование не требуются. Приёмник должен создавать карточку для разбора в статусе `draft`, сохранять исходные данные и ссылку на источник, возвращать внутренний `projectId` и статус обработки. Решение о резервировании и подтверждении заказа — отдельный шаг: заявка с сайта ещё не доказывает наличие оборудования. Нужны также управляемые сопоставления товаров, правила поиска/создания клиента по телефону, хранение контактных и логистических полей, проверка цены сайта, ограничения запросов, наблюдаемость ошибок и тесты повторной доставки. Реализацию проводить через контракты в `packages/contracts` и существующие границы модулей; не делать межсхемные SQL-запросы.

## Проверка документа при изменениях

При изменении любого упомянутого механизма агент обязан в том же изменении: сверить таблицу маршрутов и прав с кодом; обновить поля, примеры, статусы «работает/планируется» и ограничения; проверить оба вида заявок и повторную доставку, если интеграционный приёмник реализован. Дата проверки вверху должна соответствовать последней такой сверке.
