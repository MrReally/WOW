# План правок по результатам полевого тестирования

## Пакет 1 — критичные рабочие сценарии

- Мастер проекта хранит все шаги локально и создаёт проект, площадку, клиента,
  брони, роли и подрядные позиции только после финального подтверждения.
- В мастере можно создать подрядчика и сразу использовать его в позициях.
- Подрядные позиции редактируются с телефона; у каждой есть флаг
  `Забронирован`, а флаг всех позиций одного подрядчика меняется одной командой.
- События тайминга редактируются; всем назначенным участникам можно отправить
  Telegram-пинг.
- В клиентском счёте скрыты внутренние признаки подрядчика и подтверждения
  команды. Мобильный редактор категории не теряет фокус, предлагает уже
  введённые категории и показывает обозначения К / Ц / СС.
- Нижние кнопки Preview/PDF закреплены относительно экрана и не меняют
  положение при появлении клавиатуры.

## Пакет 2 — единый финансовый источник проекта

Создать в модуле `projects` сохранённые строки плановой экономики проекта:
категория, название, количество, себестоимость, цена клиенту и источник
(собственное оборудование, подряд, работа, ручная строка). Раздел `€` становится
единственным редактором. Счёт получает снимок этих строк и отвечает только за
язык, валюту, реквизиты, группировку, Preview и PDF. Версия счёта не изменяет
проектную экономику.

## Пакет 3 — единая сущность «Место»

Владельцем географических объектов должен стать модуль `venues` (переименовать
его публичные термины в `locations`, сохранив совместимость API на миграционный
период). Место содержит название, нормализованный адрес, координаты, часы работы
и контакты, а возможности задаются независимыми флагами `isVenue` и
`isWarehouse`. Складские зоны и остатки остаются в `equipment` и ссылаются на
opaque `locationId`; схемы остаются в `plans` и также используют `locationId`.
Никаких cross-schema JOIN/FK.

Миграция:

1. Расширить контракт места и таблицу `venues` без удаления старых полей.
2. Создать места для существующих складов, записать соответствие старых ID.
3. Перевести UI и сервисы на `locationId`, сохраняя чтение старых записей.
4. После проверки данных прекратить запись в старую таблицу складов.

## Пакет 4 — Google Maps, транспорт и доставка

Интеграцию разделить на независимые слои:

1. Address Autocomplete + Address Validation при сохранении места. Хранить
   отображаемый адрес, `placeId`, широту/долготу и результат проверки; ручной
   адрес разрешать с явным статусом `unverified`.
2. Новый модуль `fleet`: автомобиль, номер, модель, тип топлива, расход л/100 км,
   категория требуемых прав и эксплуатационная ставка.
3. В `people` добавить категории водительских прав с датами окончания.
4. Route Matrix считает расстояние/время между местами. Расчёт доставки хранит
   снимок маршрута, километража, цены топлива и расхода автомобиля, чтобы прошлые
   сметы не пересчитывались.
5. Совместимость человека и машины показывать как подсказку/Problem, не блокируя
   проект автоматически.

Ключ Google хранить только на сервере. Autocomplete допускает публичный
ограниченный browser key, закрытый по домену и API. Ответы маршрута кэшировать по
координатам и параметрам маршрута.

## Пакет 5 — операции и аудит данных

- Оставить проведение выдачи оборудования только в Operations на стадии
  `pickup`. Warehouse и Backoffice могут формировать/просматривать подготовку,
  но не проводить выдачу напрямую. API выдачи обязан проверять текущую стадию,
  поэтому ограничение нельзя обойти старым интерфейсом.
- Кейс Space X Wedding исследовать по append-only журналу: исходная выдача,
  ожидаемый комплект возврата, уже возвращённые ID, сторно документов и текущие
  статусы. Исправление данных выполнять компенсирующей записью, не UPDATE/DELETE
  журнала.

## Полный поток подрядчика

1. Карточка подрядчика (модуль `equipment`) хранит стабильный ID, название и
   контакты. Она доступна в справочнике подрядчиков, в мастере и в проекте.
2. Позиция подряда (модуль `projects`) хранит проект, opaque ID подрядчика, тип
   (оборудование/доставка/монтаж), название, количество, цену клиенту,
   себестоимость, заметку, флаг брони и дату возврата.
3. В проекте → «Подряд» позиции создаются, редактируются, бронируются по одной
   или все для выбранного подрядчика. Только оборудование требует возврата.
4. В проекте → `€` позиция участвует в плановой экономике. В клиентском счёте
   показывается товарная категория, но не имя/признак подрядчика.
5. В общем разделе финансов стоимость `cost × qty` попадает в задолженность
   подрядчика; цена клиенту формирует плановую выручку проекта.
6. Открытое подрядное оборудование видно в контроле возвратов до установки
   `returnedAt`. История цен доступна из карточки подрядчика.
